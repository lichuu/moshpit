## Design conventions and shared boundaries

This is a plan-only design. Proposed routes, fields, modules, and error codes below do not exist unless explicitly labeled current. Land each feature in small tested slices; do not implement this document as one branch. API changes need matching bridge validation, client parsing, fixtures, and compatibility behavior in the same slice.

Keep these current boundaries:

- `bridge/devices.mjs` is the single writer for durable device/grant state. `bridge/admin.mjs` talks to that writer over the private socket; it must not edit state files directly.
- HTTP submissions use `createSubmissions()` and its durable request fingerprint/receipt plus per-target `inLane()`. Current WebSocket input instead uses `acceptPty()` -> `writeControl()` -> a long-lived herdr control child. It does not currently enter that lane. S3-S4 must address that difference, not assume all writes are already ordered together.
- A host origin, pane ID, terminal ID, native `Agent.sessionId`, and hashed conversation-stream ID are distinct identities. Native writes bind to the native session. Conversation caches/readings bind to the stream ID plus host. Resolve pane/terminal aliases on the bridge before selecting a write lane.
- Preserve the existing `{error:{code,message}}` HTTP envelope and `Receipt` states (`delivered`, `queued`, `failed`, `unknown`). A completed fetch or `ws.send()` is not proof that the agent completed an operation. After an ambiguous write, preserve the receipt/draft and do not replay it.
- Add dependencies only where they replace protocol/security machinery that the platform does not provide. S3 proposes a maintained WebSocket server package instead of extending the current hand-written parser, and S2 (landed) adopted `request-filtering-agent` instead of hand-rolled DNS validation. Both replace security machinery, which is the whole of the exception. No new state framework, command executor, or notification service is required.

The implementation plans below supplement each feature's requirements and acceptance criteria. Policy gates remain at the end of this document. A queue orders dispatch, not necessarily backend consumption: cross-transport input requires the acknowledged ordering contract in S4.

## S3. Resource, storage, and browser protections

These initial limits were approved on 2026-09-24; validate them with normal Terminal and upload use before release. Reject overflow instead of silently truncating input or deleting files an agent may still need.

| Resource | Proposed contract |
| --- | --- |
| Active terminal sockets | 4 per device, 32 per bridge; reserve capacity atomically before upgrade |
| Terminal message | 64 KiB across a complete message, including fragments; check before accumulation |
| Pending terminal input | 256 KiB per connection, including queued work |
| Outgoing terminal buffer | 256 KiB per connection initially; disconnect a slow consumer rather than grow indefinitely |
| Client diagnostics | 16 KiB per entry, 60 entries/minute/device; reject oversized or malformed bodies |
| Upload storage | 1 GiB aggregate, including in-flight reservations; release failed reservations |
| Audit and diagnostic logs | 10 MiB per active log plus three rotated files each, as an initial bounded retention policy |

Further requirements:

- Enforce limits at shared ingress/write paths, including concurrent requests and fragmented WebSocket messages. Keep individual image validation. Quota refusal must leave existing uploads intact.
- Check ownership, file type, permissions, and symlinks before using existing push, VAPID, diagnostic, and audit files. Reuse device-store protections; refuse unsafe ownership instead of changing someone else's files. Rotation must retain those protections.
- Reject redirects on every credential-bearing client fetch, including sessions, uploads, and diagnostics. Add `Referrer-Policy: no-referrer`. Apply `Cache-Control: no-store` to protected/auth API responses and errors; leave static app-shell caching intact.
- Proposed CSP policy: derive `connect-src` from the app and explicitly configured bridge origins, including their WebSocket equivalents. Adding a host outside that list must explain the operator action needed. Approved on 2026-09-24, although it narrows current arbitrary HTTPS/WSS connectivity. The CSP browser case drives a bridge-served SPA, so it exercises the header the bridge actually emits; `vite preview` does not gain a CSP.
- Sanitize bounded diagnostic fields before appending. Do not record prompts, terminal output, uploaded bytes, content hashes, bearer/device secrets, or ticket URLs. Add terminal open/close audit events with non-secret identifiers.

Acceptance: parallel socket and upload attempts cannot exceed the cap; oversized messages, queued input, and diagnostics fail at the boundary; slow consumers disconnect. Restart accounting includes files already on disk. Unsafe files cause refusal, not repair. Redirect targets receive no credentials. Inspect logs after login, pairing, uploads, terminal use, and rotation. CSP tests preserve local fonts, workers, Markdown, authenticated images, and two configured hosts while blocking an unconfigured destination. Those tests have nowhere to run today, and the slice must supply the harness. The bridge sets CSP only on the non-API paths it serves (`bridge/index.mjs:653-657`), but Playwright serves the app from `vite preview` and `vite` (`playwright.config.ts:57,65`), neither of which emits a CSP header. Decide whether the CSP case drives a bridge-served SPA or whether the preview server gains the header, because `MOSHPIT_CONNECT_ORIGINS` "on the app-serving host" is otherwise undefined for the end-to-end path.

Integration: `bridge/index.mjs`, `bridge/upload.mjs`, existing state-file helpers, `src/lib/moshpit/{bridge,session,blackbox}.ts`, and authenticated image loading. Out of scope: automatic upload deletion, dynamic untrusted CSP origins, or a new logging service.

### S3 implementation plan

Socket transport: replace `decodeFrames()`, manual handshake, and frame encoding with a proposed direct production dependency on a maintained `ws` release, reviewed and pinned in the lockfile. It is not currently a declared project dependency; an ambient harness installation is not sufficient. Use `WebSocketServer({noServer:true, maxPayload:65536, perMessageDeflate:false})` after S4 admission. Pass Node's upgrade `head` buffer. Reject binary input for this text protocol. Keep the current JSON dump/line/size output format and validated key input, rather than inventing a terminal stream protocol.

Reserve socket capacity synchronously before asynchronous upgrade validation and count pending upgrades. An idempotent cleanup function releases the reservation on every rejection, close, and error. Use close 1002 for protocol failure, 1009 for oversized messages, 1008 for authorization failure, and 1013 for resource pressure. Check buffered output plus the next encoded payload before send; do not simply move unbounded memory into the socket library.

Track each connection's UTF-8 input bytes across the 40 ms coalescing buffer, queued writes, and in-flight control-child writes. S4 places those operations in the shared pane lane. Make `herdr.writeControl()` expose write completion/backpressure rather than swallowing errors; retain the reservation until the child stream accepts/completes the bounded write or teardown discards it. Resize messages must use the same bounded child-writer ownership. Hand-off is not backend consumption or agent completion and must not become a delivery acknowledgement or release a cross-transport ordering barrier. S4 gates use of control-child input on a verified backend acknowledgement.

Upload quota belongs at `upload.mjs:saveImage()`, below both action and submission callers. Initialize used bytes from the private upload directory, then synchronously reserve validated sizes before each asynchronous write. On success transfer reserved bytes to used bytes. On failure remove the partial file before releasing its disk accounting; failed cleanup remains charged. Return `507 upload_quota_exceeded` without deleting older uploads. The bridge process owns one counter; reconciliation after restart handles retained files.

For state/log files, extract only needed descriptor-based operations from existing private-file patterns: no-follow/nonblocking open, `fstat`, regular-file/UID/mode checks, and bounded reads. Use private temp files plus atomic replacement for push state. Serialize append/rotation per log, validate backup destinations, and rotate before exceeding the active-file cap. Do not introduce a generic persistence framework. Unsafe existing files refuse the affected operation/startup with operator guidance; permission repair is a separate approved migration.

At router entry, set no-referrer and API no-store before admission so error responses inherit them. `/api/log` uses the bounded body reader without swallowing failures, an allowlisted schema, and a per-device rolling one-minute quota. Proposed codes are `diagnostic_invalid`, `diagnostic_too_large`, and `diagnostic_rate_limited`. Keep returned messages free of submitted content. Set `redirect:"error"` at all credential-bearing fetch sites, which span `bridge.ts`, `session.ts`, `blackbox.ts`, and `uploaded-image.tsx` rather than only the central client.

CSP needs a distinct proposed `MOSHPIT_CONNECT_ORIGINS` list on the app-serving host. Incoming CORS origins and inbound authorities are not outbound bridge destinations. Generate HTTPS/WSS pairs from this list plus self; expose the public list in app discovery so Hosts can explain a rejected destination before connecting. No API response from another host may loosen the current app's policy.

Land independent slices: file/log guards -> quota/diagnostics -> client redirects/headers -> WebSocket replacement/bounds with S4 -> approved CSP. Add fragmentation/masking/head-buffer tests, slow-child/slow-client tests, concurrent quota tests, partial-write/restart tests, and hostile-file rotation tests. Preserve existing wire fixtures and verify old clients against the bounded server.

Client redirects/headers landed first, because it carries no proposed limit and no CSP change and so waits on neither open gate. Every fetch that sends a bearer, a device secret or the login password sets `redirect:"error"`: eighteen sites across `bridge.ts`, `session.ts`, `blackbox.ts`, and `uploaded-image.tsx`. The four uncredentialed discovery probes and the VAPID read still follow redirects, so a static host's redirect still reads as "not a bridge". The router sets `Referrer-Policy: no-referrer` on every response and `Cache-Control: no-store` on every `/api` response before admission, so boundary refusals, auth failures, unknown routes, and thrown errors inherit it; refused terminal upgrades carry both on the raw socket. The per-route `noStore` option is gone. Checks run: the extended header case in `bridge/security.test.mjs` (fails against the old router), a client case in `tests/unit/access.spec.ts` that drives every credentialed call and fails against the old client, typecheck, lint, 212 bridge tests, and the Chromium phone and desktop Playwright projects (176 passed, 22 skipped, after the `/api/log` fix below; the first run reported here as passing had 27 bridge-backed failures that were missed). No-store exposed a Chromium behavior: a keepalive request is never reported finished when its no-store response has a body, so the black box's heartbeat kept every bridge-backed page from reaching network-idle. `/api/log` now answers an empty 204, which keeps no-store. The Firefox and WebKit security projects did not run locally for lack of their browser builds; CI runs them. Remaining limitations: `uploaded-image.tsx` is a component and is covered by inspection, not by that client case; the redirect refusal is asserted on the request options, not by a browser following a real 3xx. The limits, retention and CSP were approved on 2026-09-24, so every remaining S3 slice is now schedulable; file/log guards came next.

File/log guards landed second, in `bridge/private-files.mjs`. The VAPID key pair, the push store, `audit.jsonl` and `client.log` now open with no-follow/nonblocking flags and an `fstat` check. A symbolic link, a non-regular file, a file owned by another user, or a file larger than this bridge writes is refused, and never repaired. Our own file with a loose mode is tightened to 0600, following the device store. At startup the bridge checks all four and exits 1, naming the path and the operator action, instead of failing on the first request; the check creates nothing. VAPID and push state are replaced through a private `O_EXCL` temp file and an atomic rename, which refuses to replace a link. Both logs append through one serialized lane. They rotate before a line would pass 10 MiB and keep three backups. Every backup destination is validated before anything moves, so a planted `.2` link refuses rotation without touching its target or the active file. Checks run: `bridge/private-files.test.mjs` (read, write, mode, foreign-owner, rotation, planted-link and no-create cases; the foreign-owner case needs root and skips otherwise), a startup case in `bridge/security.test.mjs` for each of the four paths that fails against the old bridge, 221 bridge tests with 2 skipped, typecheck, and lint. Remaining limitations: `/api/log` still swallows append failures and has no schema or rate limit; that belongs to the quota/diagnostics slice, which comes next. Upload and submission state are out of this slice's scope.

Quota/diagnostics landed third. `createUploads()` in `bridge/upload.mjs` now owns uploads for both the action and submission callers. It holds a 1 GiB aggregate quota. Usage starts from the files already in the uploads directory, and each save reserves its decoded size synchronously before writing, so parallel uploads cannot overshoot. A refusal is `507 upload_quota_exceeded` and deletes nothing. It then reads at most 16 KiB (`413 diagnostic_too_large`) and keeps only the black box's own fields through an allowlist in `bridge/diagnostics.mjs`, each bounded. Unknown kinds, unknown fields and mistyped values are `400 diagnostic_invalid`, and no refusal echoes what was sent. Append failures now reach the client rather than being swallowed. Each record names its device. Checks run: `bridge/upload.test.mjs` (parallel overshoot, restart accounting, validation before reservation, and release after a failed write, which works as root), `bridge/diagnostics.test.mjs`, an HTTP case in `bridge/security.test.mjs` that fails against the old handler, 229 bridge tests with 2 skipped, typecheck, and lint.

The WebSocket replacement landed fourth, after S4 had made the socket output-only. `ws` 8.21 is now a pinned production dependency (`npm audit --omit=dev`: 0 vulnerabilities), and the hand-written handshake, frame decoder and encoder are gone. `WebSocketServer({noServer:true, maxPayload:65536, perMessageDeflate:false})` takes the upgrade with Node's `head` buffer after the S4 admission checks. A message over 64 KiB, fragments included, closes with 1009; binary input closes with 1003; a wrong target and an authorization failure close with 1008. Capacity is 4 terminal sockets per device and 32 per bridge. It is reserved synchronously when the upgrade consumes its ticket, before any await, and released idempotently on refusal, handshake failure, close and error. Over the cap is `429 terminal_device_limit` or `503 terminal_limit`. Every outgoing frame is checked against a 256 KiB bound on what the socket already buffers, and a consumer that falls behind is closed with 1013. The pending-input bound in the table no longer applies, because sockets accept no input. Checks run: new cases for the per-device cap with parallel upgrades, slot release on close and on five refused upgrades, oversized and fragmented-oversized messages, fitting fragments, binary input, and a paused consumer receiving 1013; the raw test client now answers close frames as a browser does; 239 bridge tests with 2 skipped, and lint. Remaining limitations: the 32-socket bridge cap is not exercised by a test.

The approved CSP landed last, so S3's listed slices are all in. `MOSHPIT_CONNECT_ORIGINS` is a new optional list, parsed with the same strict origin rules as the other allowlists; a malformed member refuses startup. ## S4. Terminal authorization and input safety

Requirements:

- Re-resolve target existence and ticket binding immediately before returning HTTP 101. A pane disappearing or changing identity after issuance must not attach to a replacement.
- Add strict query-shape validation to the upgrade path. `openTerminal()` reads only `ticket` (`bridge/index.mjs:971`) and the client sends only `ticket`, so there are no legacy `token`, `device`, or `target` parameters to reject; what is missing is rejection of unknown and duplicate parameters, which `searchParams.get` currently resolves to the first value. Keep single-use ticket consumption.
- Close established sockets when their identity session or device approval expires. Decided on 2026-09-21: this already works, so the slice is tests only. `pump()` calls `authorized()` on every tick and reschedules itself every `PTY_POLL_MS` (100 ms) whether or not input arrives (`bridge/index.mjs:426,459`), and `authorized()` calls `requireActiveTicketOwner()` plus `activeDevice()`, which rejects on both `revokedAt` and expiry (`bridge/devices.mjs:397`). An idle socket with dead credentials therefore closes within about 100 ms. Do not add a deadline scheduler; both checks are in-memory lookups. Prove expiry-without-input and revocation-during-input with a controllable clock rather than long sleeps.
- Route touch and hardware input through the existing shared validation. An unsupported modifier combination must be rejected with visible feedback, not reduced to a different key. Current `parsePaneKey()` checks modifiers only for some keys: Ctrl+Arrow delivers an unmodified arrow; Shift+, Ctrl+, and Meta+Enter deliver a plain Enter, which submits; Ctrl+Tab delivers Tab; and Ctrl+ or Alt+Backspace delivers Backspace. This safety fix does not require supporting every hardware key.
- Rejected, expired, stale, or malformed input dispatches zero backend commands. Do not automatically replay a write after disconnect or uncertain delivery.

Acceptance: test target removal/replacement between ticket issuance and upgrade, consumed tickets, mixed legacy/ticket URLs, revocation during input, and expiry without new input. ## S7. Browser-led and headless Linux deployment

The checkout-based helper, systemd user service, device CLI, and browser self-pairing are existing foundations. They are not the proposed installer. Ship this in two testable parts; do not make a pretty wizard hide incomplete host setup.

### S7a. Install and maintain the host

- Distribute versioned Linux x64/arm64 releases as one executable each, holding the bridge, the launcher, the Node runtime and the built PWA (see S7d and Runtime and packaging below). Publish checksum verification instructions, and say what a checksum does not protect against. Users must not need a checkout or npm build.
- Before changes, check architecture, systemd user-service support, signed-in Tailscale, and usable herdr connectivity. Derive the trusted owner from the local node's user ID and matching user record, never the first login. Explain unsupported tagged-node setups.
- Use schema-validated XDG config/state with private permissions. Migrate legacy environment settings through a strict parser, never shell sourcing. Preserve supported password modes and device state.
- Fresh setup prefers HTTPS 443, then 8803 if occupied. Refuse conflicts on both. Reruns, migration, and updates preserve the configured HTTPS origin and unrelated Serve routes; report conflicts instead of silently moving origin. Never enable Funnel.
- Run as a user service. Ask before OS authorization or persistence-after-logout changes. Persist completed installation steps and resume unfinished setup on rerun without resetting approvals. Mark setup complete only after the real HTTPS path, identity, herdr connectivity, and service persistence checks succeed.
- Provide `moshpit setup`, `status`, `update`, and `uninstall`. Verify updates before switching, retain the prior release for rollback, and preserve approvals. Uninstall preserves state unless explicitly requested otherwise. Roll back only changes made by this attempt.

Acceptance: fresh install without cloning/building; interrupted rerun; existing-origin conflict; rejection of an update that does not match its manifest; successful rollback; strict legacy migration; unsupported prerequisites fail before mutation. Verify reboot persistence and that unrelated Serve services continue working.

### S7b. Bootstrap and enroll browsers

Builds on the current enrollment rule: only the private admin socket issues grants, and identity alone never approves a device. Proposed policy extends private local bootstrap with approval of a particular new-device request by an already-approved device.

- The local launcher issues a five-minute, single-use, owner-bound bootstrap capability through the private admin socket. Open the final HTTPS setup URL with the capability in its fragment, remove it immediately, and redeem in a request body under the expected identity. Setup APIs cannot execute arbitrary commands or change the owner.
- Confirm the machine/account, approve the browser, and open its herd without an Add host form. If automatic browser launch fails, show how to open the short-lived link manually, including from a headless Linux host. Setup/enrollment links bypass introductory slides; a reload during the setup-link confirmation drops the link, which lives only in memory, and lands on the normal screen, so the person opens the link again; a reload never replays a consumed capability, and existing approved browsers return to their herd.
- Additional devices create bounded, rate-limited five-minute requests bound to a browser-held random secret and owner. An approved browser sees a matching verification phrase and explicitly approves/rejects that request. The phrase is not a secret. Approval permits one atomic redemption only.
- Share an address-only QR plus a copyable address. Explain phone-side Tailscale access. Request notification permission only when enabled. An installed PWA lacking credentials enrolls normally rather than assuming credentials transferred from the browser.
- Explain pending, rejected, expired, and lost-response states. A consumed bootstrap response lost before storage requires explicit local `setup --recover`; an additional browser requests fresh approval. Never replay a consumed capability or automatically reopen first-device enrollment after revocation.
- Treat an empty herd as connected and explain how to start an agent. Keep phone enrollment, installation, and notification setup optional and accessible later through Hosts.

Acceptance: host bootstrap and phone enrollment through the real HTTPS origin, including manual link opening and reload/resume. Wrong-owner, expired, replayed, and unauthorized attempts fail; concurrent redemption yields only one enrollment. Revoked credentials cannot approve enrollment, but a formerly revoked browser with valid identity can redeem a freshly authorized grant. Lost responses preserve existing approvals; setup secrets never appear in logs, referrers, or caches. An installed PWA without credentials can recover through enrollment. Release requires V1 on the candidate bundle.

### S7c. Headless setup for servers

Requested 2026-09-25. A server with no desktop or browser, reached over SSH or provisioned by automation, must be able to do everything the browser wizard does. S7a and S7c share one setup engine: the same preflight, journaled state machine, config, Serve handling, verification, bootstrap capability and enrollment records. The browser wizard and the headless CLI are two front ends to that engine, not two implementations. A step that works in one and not the other is a defect in both.

| Wizard step (S7a/S7b) | Headless equivalent |
| --- | --- |
| Preflight with repair instructions | Same checks and the same wording on stderr, with a distinct exit code per failed check, before any mutation |
| Confirm the detected machine and account | Printed, then an interactive prompt on a TTY; `--yes` accepts what was detected and nothing else |
| Choose the HTTPS origin (443, else 8803; preserve on rerun; conflicts refuse) | The same rules. `--port` may only *request* 443 or 8803 on a fresh install, and still refuses a conflict. No flag moves an existing origin |
| OS authorization and persistence after logout | Never implied by `--yes`. Separate explicit flags (proposed `--allow-linger`); without them on a non-TTY, stop and report the step as blocked |
| Open the setup link in a browser | Detect no display (`DISPLAY`/`WAYLAND_DISPLAY` unset, or an SSH session) and do not try to launch one. Print the short-lived HTTPS setup link, and on a TTY a terminal QR of the same link, for opening on another tailnet device. The capability stays in the fragment, expires in five minutes, is single-use and owner-bound, and is printed only to the invoking terminal: never to logs, and never in `--json` output unless stdout is a TTY or `--emit-link` is given |
| Wait for "Finish setup" | `setup` waits, with a visible countdown, until the capability is redeemed or expires; Ctrl-C leaves setup resumable. An expired link is replaced by rerunning `setup` while the host awaits its first device; a response lost after redemption needs `setup --recover`. Neither replays a capability |
| Approve an additional device from an approved browser | `moshpit devices pending` lists requests from `/api/enrollment/request` with name, phrase and age, never secrets. `moshpit devices approve <id>` and `reject <id>` go through the private admin socket, show the phrase, and ask for confirmation unless `--yes`. The local shell is already the enrollment trust root (admin-only pairing), so this adds no weaker path |
| Show the address-only QR and copyable address | `moshpit address` prints both; the QR holds no secret |
| Status, update, uninstall, recover | Already CLI (S7a). Each accepts `--json` |
| Setup complete | Headless setup can verify the service, herdr connectivity and the HTTPS path from the host, but not a real browser identity. It reports `installed, awaiting first device` until the first enrollment redeems, then `complete`. `status` shows which |

Requirements specific to headless use:

- Everything is a subcommand with flags. No step needs a TUI, a pager or an editor. Prompts appear only on a TTY; on a non-TTY a needed answer that was not given as a flag is a blocked step with its own exit code, never a guessed default.
- `--json` emits one machine-readable result per command, `{ok,state,steps:[{id,status,detail}],next?}`, suitable for cloud-init, Ansible or CI. The setup link appears in JSON only when stdout is a TTY or `--emit-link` is given, because automation logs are not a safe place for a capability.
- Idempotent: rerunning `setup` with the same flags on a finished host changes nothing and exits 0; on an unfinished host it resumes from the journal.
- Unattended first-device enrollment without any human is out of scope. Someone must open the link or approve a request; a pre-approved device credential is never generated for automation to copy.

Acceptance: the S7a/S7b acceptance cases pass through the CLI on a host with no display: fresh install, interrupted rerun, origin conflict, missing prerequisites (each with its exit code), a first device enrolled from a phone via the printed link and via the terminal QR, `--recover` after expiry and after a lost response, an additional device approved and rejected with `devices approve` and `reject`, and a revoked device unable to approve. `--json` output validates against its schema; the capability never appears in a non-TTY log without `--emit-link`. The browser wizard and the CLI produce identical journal and device state for the same host.

Design, recorded 2026-09-28: the host steps always run through the one setup engine, from the CLI (`moshpit setup` on a host, or through `docker compose exec` in the container). The browser front end is the setup link: setup opens it in a local browser on a desktop session or prints it with a QR, the browser confirms the machine and the Tailscale account, the person approves, and the browser opens its herd. No second implementation of the host steps runs in the browser. The acceptance item "the browser wizard and the CLI produce identical journal and device state for the same host" therefore holds by construction: one engine writes the journal, and one grant path (the admin pairing grant, redeemed at `POST /api/devices/pairing`) writes device state, whichever front end the person uses. That is how that acceptance item is met.

### S7d. Self-installing binary and container image

Requested 2026-09-26: people must be able to deploy moshpit to their own servers easily. v1 offers two server paths, both front ends to the S7a/S7c setup engine rather than separate installers. There is no `curl | sh` script: piping a remote script into a shell runs unverified code before any signature check, which contradicts S7a's signed-release requirement.

**Self-installing binary.** The release is one file per architecture, `moshpit-linux-x64` and `moshpit-linux-arm64`, holding the bridge, launcher, Node runtime and built PWA as embedded SEA assets. The documented install is three visible steps: download the file, check its SHA-256 with one documented command, then run `./moshpit setup`.

- Verification happens before anything executes. Since 2026-09-27 it is a SHA-256 and size check against the release manifest, downloaded over HTTPS from GitHub; releases are not signed (see Decisions). The release page gives the exact command.
- `setup` copies the verified binary into `$XDG_DATA_HOME/moshpit/releases/<version>`, points `current` at it, and continues the S7a/S7c flow. The downloaded file can be deleted afterwards. Later updates use `moshpit update`, which verifies against the key embedded in the running release, so only the first download relies on the user's check.
- Rerunning `setup` is idempotent on a finished host and resumes an unfinished one.
- It needs no root and no Node, npm or checkout. It refuses to run as root, and prints the commands to create an unprivileged user and rerun as that user. The only privileged step is linger (persistence after logout), which a server needs: it is prompted on a TTY and requires `--allow-linger` otherwise (S7c).
- On an unsupported host (musl libc, no systemd, a missing prerequisite) preflight fails before mutation, names the missing piece, and points to the container image where that fits.
- Publish a cloud-init example that downloads a pinned version, verifies it, and runs `setup --yes --allow-linger --json` as an unprivileged user, ending at `installed, awaiting first device`, plus the step that prints the enrollment link over SSH.

**Container image.** Because the bridge drives herdr and herdr runs the agents on the same host, the image is a complete agent host, not a bridge-only image:

- One multi-arch (x64/arm64) image on a glibc base with the bridge executable and herdr. Agent CLIs are not baked in: document a derived-image pattern (`FROM moshpit` plus the user's chosen CLIs) and publish one example. Signed with a published key or keyless signature, and documented by digest as well as tag.
- Tailscale runs as a sidecar sharing the container's network namespace, and Tailscale Serve in the sidecar proxies HTTPS to the loopback bridge, so the bridge still binds loopback only and never enables Funnel. Owner derivation needs a user-owned node, so the example uses an untagged auth key or an interactive login; a tagged-node auth key is refused at preflight with the same explanation as S7a.
- The container's restart policy replaces the systemd user service and linger; the setup engine records the service step as container-supervised rather than skipping it. Setup, enrollment and device approval run as `docker exec <container> moshpit setup|devices|address`, with the same output, exit codes and `--json` as S7c.
- Volumes: config, bridge state (devices, uploads, journal), herdr state, workspaces, and agent credentials. Document that the agent-credential volume holds secrets and must not be shared. Run as a non-root user inside the image.
- Updates are new image tags, not `moshpit update`. The S7 state rules still apply: the bridge refuses to start on a state schema it cannot read, and rolling back to an older tag never restores an older device database.
- Publish a Compose file with the moshpit and Tailscale services and the volumes above.

Acceptance: the verified binary, run on a clean glibc systemd x64 and arm64 server over SSH, reaches `installed, awaiting first device` with no root, no Node and no checkout; it also works from the cloud-init example; a tampered binary fails the documented verification, `moshpit update` rejects a tampered release, and a musl host and a root user each fail before mutation with their own exit codes; a rerun changes nothing. The Compose example, started on a clean host with Docker, reaches the same state, enrolls a phone through the printed link, survives a container restart and a host reboot with devices intact, and upgrades to a new tag with approvals preserved. A tagged auth key is refused. Both paths pass the S7c acceptance cases that apply to them.

Integration: `scripts/bridge.sh` and `deploy/bridge.env.example` are committed (#50) but remain checkout-based helpers, not release assets; the release binary and image replace them for users, and packaging must build reproducibly from a clean checkout. Extend `bridge/admin.mjs`, device state/API handling, `onboarding.tsx`, `hosts.tsx`, `runtime.tsx`, and `store.ts`. Out of scope: public hosting, multi-user enrollment, automatic agent creation, distro packages (AUR, .deb, .rpm), and other host operating systems in v1.

### S7 implementation plan

Host layout, proposed: private config at `$XDG_CONFIG_HOME/moshpit/config.json`, state at `$XDG_STATE_HOME/moshpit`, immutable versioned bundles below `$XDG_DATA_HOME/moshpit/releases`, and one `current` pointer used by the user service. Config fields include `schemaVersion`, `authMode`, `trustedOwner`, `publicOrigin`, `allowedAuthorities`, `allowedOrigins`, `connectOrigins`, `bind`, `port`, `herdrBin`, and `stateDir`; preserve a private password-file reference for compatibility modes. Reject unknown keys and malformed origins before creating a service.

Storage format, decided 2026-09-26: the config stays a private JSON file and bridge state stays in the existing private files. Neither moves to SQLite, encrypted or not. The bridge starts unattended as the host user, so a decryption key would sit on the same disk under the same UID as the data, and anyone who can read the 0600 files can read the key. The state that would matter holds little plaintext anyway: device and grant secrets are stored as SHA-256 hashes, and the config holds origins, a login and paths, with the password in its own file. SQLCipher is a native module, which works against the S7d single executable, and `node:sqlite` has no encryption. The one plaintext secret at rest is the VAPID private key. S7d may read it and the password file from a systemd or container credentials directory (`LoadCredential=`, Docker secrets) instead of the state directory. Full-disk encryption covers stolen hardware and is an operator recommendation, not bridge code. Revisit only if the bridge gains a secret that a same-UID reader must not see, and only with a key held off that disk.

Runtime and packaging, decided 2026-09-26: keep the bridge on Node and ship it as a Node single executable application built with `node --build-sea` (added in 25.5) on Node 26, which is expected to enter LTS in October 2026. The bridge is I/O glue (HTTP, `ws`, child processes, files, `node:crypto`, `web-push`, `request-filtering-agent`), so no runtime is faster in a way users would notice. Staying on Node keeps the tested code and the S2-S4 security evidence valid. SEA is still labelled Experimental in the Node documentation, so the packaging slice must gate on the full bridge suite plus a WebSocket, push and upload round trip run against the built binary on x64 and arm64. If the binary fails that gate or is too large, evaluate `bun build --compile` against the same gate next; its compatibility risk sits in exactly the paths S2 and S3 hardened (`ws` upgrades on Node's `http` server, `web-push` ECDH, and `request-filtering-agent`'s `http.Agent` hooks). Deno is not preferred: its npm compatibility is lower and its permission model adds little to a process that must spawn herdr, Tailscale and systemd. A Go or Rust rewrite is out of scope unless measured size or memory on a small arm64 host requires it, because it would restart the bridge's tests and security evidence. Official Node binaries, and therefore the SEA, need glibc; the S7d binary refuses musl hosts such as Alpine and points them to the container image, which uses a glibc base.

Use one small Node launcher inside the same executable, sharing bridge validation, with literal argv calls to Tailscale/systemd/herdr. Do not source legacy configuration. The bundle manifest names release/architecture/Node version, file hashes, and compatible config/state versions. Select release hosting, signing-key custody, trusted-key distribution/rotation, and archive verification before claiming secure installation; a checksum beside an unsigned archive is insufficient. A proposed packaging script must build from a clean checkout and include production dependencies without a local `.agents` directory.

Installer state machine: `preflight -> staged -> configured -> service-started -> serve-configured -> verified -> complete`. Hold a single-installer lock. Atomically journal completed steps and previous values for resources changed by this attempt, never setup capabilities. On resume, compare actual resources with the journal before skipping or undoing work. Rollback restores only still-owned values; a concurrently changed Serve route is a conflict, not permission to overwrite it.

Stage and verify updates before atomically moving `current`; restart and health-check, then retain the previous bundle. Never restore an older device database as rollback, because that could resurrect revoked devices. Reject a rollback binary that cannot read the current security state schema. Report configured service persistence separately from a successful physical reboot check.

Enrollment reuses the device store's serialized replacement. Bootstrap can reuse an admin-issued five-minute grant; add request-specific enrollment records only for the approved-device flow. Proposed record: `{id,owner,name,secretHash,expiresAt,status,approvedBy?}`, where status is `pending | approved | rejected | consumed`. Compute expired as a terminal condition from expiresAt. Limit outstanding grants plus requests to eight initially and retain the existing state-size ceiling; never store a plaintext browser secret.

Proposed API contracts, all behind the existing browser boundary:

| Route | Required authority | Request / result |
| --- | --- | --- |
| `POST /api/enrollment/request` | Identity | `{name}` -> `{id,secret,phrase,expiresAt}` once |
| `POST /api/enrollment/status` | Identity + request secret | `{id,secret}` -> public request status |
| `GET /api/enrollment/requests` | Identity + approved device | Pending requests for that owner, no secrets/hashes |
| `POST /api/enrollment/decision` | Identity + approved device | `{id,decision:"approve"|"reject"}` -> status |
| `POST /api/enrollment/redeem` | Identity + request secret | `{id,secret}` -> existing device credential response once |

Creation uses the pairing creation limit; status polling is bounded per request/owner and client polls no faster than every two seconds. Approval revalidates the approving device inside the serialized mutation. Redemption checks owner, expiry, request secret, status, and the approving device's continued authorization, then consumes and creates the device in one commit. Revoked approvers invalidate pending approvals; local-admin recovery remains available. No identity-only route may list other requests or approve them.

Client setup must capture and remove the fragment at app entry before breadcrumbs or asynchronous discovery, not in a late component effect. Keep a bootstrap capability only in memory and forward it only to the serving origin. For additional enrollment, store the scoped request secret in short-lived session storage so a same-tab reload can resume; purge it on expiry, rejection, redemption, or cancel. A different PWA storage partition starts its own request. Persist presentation steps separately from authorization and never auto-reissue a consumed capability.

After successful redemption, save credentials using `access.ts`, validate them with a protected read, upsert the same-origin host, then connect. Lost responses require new authorized recovery. Build/test in slices: reproducible bundle/config -> journaled host setup (with its headless front end and `--json` from the start) -> bootstrap client (browser, plus printed link and terminal QR) -> request/approval flow (browser approval and `devices approve`/`reject`) -> updates/rollback -> self-installing binary and cloud-init example -> container image and Compose example. Use command-runner fixtures and crash injection at every journal/store transition before clean-host and physical-phone acceptance.

Config landed first, as the config half of the reproducible bundle/config slice. `bridge/host-config.mjs` holds one field table that maps each config key to its legacy variable and a value kind; parsing, the env conversion and migration all iterate it. `MOSHPIT_CONFIG` names a JSON file that the bridge reads through `readPrivateFile`, so a symbolic link, a non-regular file or a foreign owner refuses startup. The file must have `schemaVersion` 1 and known keys of the right kind. Its values then pass through the bridge's own `createBrowserBoundary` and the now exported `readIdentityConfig`, which never opens the password file. A loaded config becomes exactly the environment variables it stands for, so every downstream reader is unchanged; a variable set in both places refuses startup. `node bridge/host-config.mjs migrate` parses a legacy env file strictly, never through a shell: it refuses `export`, quotes, `$`, backticks, backslashes, NUL, whitespace anywhere in a value, repeated and unknown names, `MOSHPIT_PASSWORD`, development settings, and relative paths, naming the line and variable but never the value. Values that reach the bridge's own origin and identity checks get those checks' messages, which quote origins and modes as the environment path always has. It writes the config 0600, creates a missing parent directory 0700, and refuses to replace one; `check` validates it. Checks run: `bridge/host-config.test.mjs` (13 cases, including a round trip of `deploy/bridge.env.example` and three bridge startups), each confirmed to fail against a seeded defect in the check it covers (16 mutants, all caught); 258 bridge tests with 1 skipped; typecheck; and lint. Remaining limitations: `scripts/bridge.sh` and the systemd unit it writes still use `deploy/bridge.env`; the config does not yet default to the XDG path; `bind` is checked for loopback only when the bridge starts, not by `check`; `MOSHPIT_SERVE_PORT` is refused by migration because only the helper script reads it; and `bridge/admin.mjs` still finds the state directory only through `MOSHPIT_STATE_DIR` or `--state-dir`, not the config. It writes `dist/release/moshpit-linux-<arch>` and a manifest with the name, the `git describe --always --dirty` version, the arch, the Node version, `configSchemaVersion`, the SHA-256 and the size. `bridge/cli.mjs` is the executable's main and also runs from a checkout: `bridge` imports `index.mjs`, while `admin`, `config` and `version` never start a server. The run-as-main guards in `admin.mjs` and `host-config.mjs` now also require `!isSea()`, because every module in the executable shares one `import.meta.url` and both guards fired at startup. `serveSpa` reads through `bridge/spa-source.mjs`, from disk in a checkout or from the embedded assets, with a content-hash etag and the same cache, traversal, fallback and MIME rules. `node --build-sea` records the main script's path, so the build names it relatively. With that, two consecutive builds from one clean tree were byte-identical, and so was a build from a copy of the tree at another path. The x64 executable is 66,035,312 bytes, about 2.8 MB more than the Node binary it wraps. It answered its first `/api/auth-info` with 200 about 75 ms after spawn, against about 95 ms from source. The run had 264 tests, 263 passed and 1 skipped (the root-only ownership case), with 75 bridge launches from the executable covering WebSocket (`write-routing.test.mjs`), push registration (`pair-push.test.mjs`, `security.test.mjs`) and a new accepted image upload round trip. `bridge/cli.test.mjs` (4 cases) and `bridge/release.test.mjs` (the embedded SPA with the CSP, the index fallback and an immutable hashed asset whose etag is its SHA-256; skipped without the executable) were confirmed to fail against seeded defects: `cli.mjs` importing `index.mjs` statically failed all four cli cases from source, and an executable built with the old guard failed all four against the binary. `npm run test:bridge` from source: 264 tests, 262 passed, 2 skipped. Setup landed third, as the journaled host setup slice with its headless front end. `moshpit setup` and `moshpit status` are in `bridge/cli.mjs`, both with `--json`; setup also takes `--yes`, `--allow-linger` and `--port 443|8803`. `bridge/host-probe.mjs` runs every external command through one runner (`execFile`, literal argv, no shell) from a named command table, and parses Tailscale, Serve and systemd output with pure functions: the owner is the user record for `Self.UserID`, and a non-empty `Self.Tags` means tagged. `bridge/host-steps.mjs` holds two tables. `CHECKS` has one row per preflight check, each with its own exit code (10 to 22: release, unit-safe paths, arch, libc, user, systemd, legacy service, Tailscale, owner, config, herdr, HTTPS port, bridge port); rows run in order before any change and fill in the plan. The config row reads the journal: once it records `configured` or `serve-configured`, a missing config refuses with exit 18 and the journaled origin instead of being treated as a fresh host, so a rerun cannot move the origin or count setup's own Serve route as taken. The paths row (exit 22) refuses a data or config path holding a quote, backslash, `$` or control character, because systemd reads an executable path literally; spaces and `%` are quoted and kept. `STEPS` is the state machine staged, configured, service-started, persistence, serve-configured, verified; each step has `isDone` (reads the host), `snapshot` (the value it replaces), an optional `conflict`, and `apply`. `bridge/host-setup.mjs` walks them. It re-checks every step on the host even when the journal says done, re-applies drift, and refuses conflicts (exit 33). The journal `$XDG_STATE_HOME/moshpit/setup.json` holds `{schemaVersion:1, steps:{id:{at,previous}}}` and is written atomically; the previous value is journaled before apply, so a crash cannot lose it, and `at` is set only after the step verifies. A resumed unfinished entry keeps its previous value; a step applied again after it finished records what that attempt replaced. The service step refuses (exit 33) a `moshpit.service` whose text is not exactly what setup renders, and journals only the SHA-256 of a unit it replaces, never its text. This splits the planned `apply -> {previous}` into `snapshot` then `apply` for that reason. The service step issues `daemon-reload` and `enable --now` only while systemd still needs them, so a resumed run never repeats a command that took effect. Lingering is its own step: prompted on a TTY, run with `--allow-linger`, otherwise blocked with exit 32 while the remaining steps continue; `--yes` accepts only the detected machine and account. A non-TTY run without `--yes` stops before any change (exit 30). The lock is `setup.lock` holding the pid, linked into place already written, taken over when its pid is dead (exit 31 otherwise). Signing landed fifth, as the prerequisite for signed updates and rollback. It was removed on 2026-09-27 (see Signing removed, below, and Decisions); this paragraph records what landed then. Requests landed seventh, as the request/approval half of S7b. The device store (`bridge/devices.mjs`, still the single writer) moves to state version 4, which adds `requests: [{id, owner, name, secretHash, createdAt, expiresAt, status, approvedBy}]`. `status` is `pending`, `approved`, `rejected` or `consumed`; expired is computed from `expiresAt` and never stored. `createdAt` is added to the planned record so the list can show an age. Update landed eighth, as the signed updates and rollback slice, together with uninstall. `moshpit update [--version <tag>]`, `rollback` and `uninstall [--purge] [--yes]` are in `bridge/cli.mjs`, each with `--json` and the same result shape and lock as setup. `bridge/release-source.mjs` fetches `releases/latest` or `releases/tags/<tag>` from GitHub (`MOSHPIT_RELEASE_API` overrides the base), then the arch's executable, manifest and both signatures. ## S8. Scoped command discovery

Current: bounded partial discovery is implemented in this slice. `GET /api/commands` is scoped when either `target` or `sessionId` is present (both required; unknown, repeated and kind/path parameters are refused): the bridge resolves the pane and its exact native session from a fresh snapshot before scanning and re-checks pane, session, kind, cwd and worktree root from another fresh snapshot after, returning `404` for an unknown pane and `409 command_scope_changed` for any drift. One shared two-second deadline and AbortSignal covers both snapshots, the targeted fresh project lookup and the scan; read-only herdr subprocess waits honor it and owned timed-out children are killed; nothing is published after a stop. Scanning is bounded jointly across all sources (200 results, 1,000 examined entries, depth 8, 256 KiB per metadata file) with stdlib `opendir` and descriptor reads, canonical-path cycle breaking, and categorical warnings that carry no paths; the revision fingerprints inspected source identity/stat metadata and diagnostics. The catalog carries scope, revision, coverage, truncation, prefixes, entries with bounded origin labels and warnings; every supported home/XDG inventory reports `partial`. The client keys discovery state by host/pane/session/kind/project/refresh, renders only the matching key (failures included), aborts and ignores stale responses, and guards insertion against a moved scope or draft revision. The spawned-Pi RPC discovery (`bridge/pi-commands.mjs`) and its client upgrade request are deleted; a pi pane gets the partial disk catalog and no process is started. The kind-only legacy route remains for pre-scoped clients, explicitly partial, in its old shape. Retry rescans without touching the draft.

Remaining: the attached-harness registry half (per-harness project/config sources and full installed-catalog comparison for Claude, Codex, Pi, Grok and OpenCode) is still probe-gated; assistive-technology verification of the input/listbox pattern and physical-device runs are outstanding. ### S8 implementation plan

Decided as the bounded partial slice was implemented in this slice: the scoped route and the legacy kind-only route keep separate response shapes; the client parses only the scoped shape (`parseScopedCommandsResponse`), the legacy shape is served for pre-scoped clients and no longer parsed in this app, the project equality token is `JSON.stringify([projectRoot ?? null, cwd])` over existing snapshot metadata, and the one shared two-second deadline covers pre-scan snapshot, targeted project lookup, scan and post-scan snapshot.

Replace the kind-only request with `GET /api/commands?target=<pane>&sessionId=<native-id>`. Resolve the current agent from the bridge snapshot, require the expected native session, and derive project/config roots on the host. A mismatch returns `409 command_scope_changed`. Keep any legacy kind-only route explicitly partial during client migration; it must not claim scoped discovery. The old client parser validated a single `prefix` against a closed enum and rejected any invocation not carrying it, while the scoped catalog carries `prefixes: string[]` and no `kind`; the shapes stayed separate, so the client parses only the scoped shape and the legacy route keeps its old shape for pre-scoped clients.

Proposed response shape:

```ts
type CommandCatalog = {
  scope: { target: string; sessionId: string; project: string };
  revision: string;
  coverage: "full" | "partial" | "unsupported";
  truncated: boolean;
  prefixes: string[];
  commands: { name: string; invocation: string; description: string; origin: string }[];
  warnings: string[];
};
```

`project` and revision are bridge-derived opaque scope metadata, not client filesystem selectors. `origin` is a bounded category/display label, not a credential-bearing configuration dump. A verified harness registry adapter may produce full coverage; current home/XDG scans remain partial. An adapter must read an existing supported interface, not start a new agent or run arbitrary discovery commands. Establish and test source precedence per installed harness before merging duplicates.

Bound scanning work as well as output: proposed initial caps are 200 results, 1,000 examined entries, depth eight, 256 KiB per metadata file, and a two-second request budget. Stop traversal before exceeding a cap and return partial/truncated warnings. Check cancellation between reads, canonicalize visited paths to break symlink loops, and use bounded reads instead of reading an entire file then slicing it. Missing/unreadable sources differ from a valid empty catalog.

**C3. Changes sheet.** Proposed `GET /api/changes?target=<pane>` answers "what has this agent changed so far?". The bridge resolves the cwd or worktree from the herdr snapshot, never from a client path. It runs literal-argv git (`status --porcelain`, `diff --numstat`, `diff`), includes untracked but never ignored files, and returns a file list plus a patch capped at 3 MiB with a `truncated` flag, `no-store`. Current: landed on 2026-10-10. `GET /api/changes?target=<pane>` (`bridge/changes.mjs`, wired in `bridge/index.mjs`) takes the pane and nothing else: any other parameter, a repeated one, an empty or dash-led target is `400 changes_request_invalid`, and the directory is the herdr snapshot's `foreground_cwd || cwd` for that pane. The answer is `{kind:"not-a-checkout"}` (a clean answer, nothing to warn about) or `{kind:"checkout", branch, detached, counts:{staged, unstaged, uncommitted, untracked, unpushed}, unpushedBasis, truncated}`, `no-store`. Any failure is the C3 envelope `{error:{code,message}}` with the same statuses and codes, and the client reads every one of them (and a timeout, an offline bridge, or an answer its schema rejects) as "could not check". Git runs in the toplevel as `rev-parse --show-toplevel`, `rev-parse --git-path index`, `config -z --name-only --get-regexp ^filter\.`, `status --porcelain=v2 --branch --ahead-behind -z --untracked-files=all --ignore-submodules=all`, and then at most one of `remote` plus `rev-list --count --max-count=1000 HEAD --not --remotes --`, or `rev-list --count --max-count=1000 HEAD --not --branches --remotes --`. There is no `fetch`, `ls-remote`, `pull` or `push`, and no network: a test points `origin` at an address nothing listens on and the read still returns at once. `staged` counts entries with a change in the index column, `unstaged` entries with one in the worktree column (a conflict counts here), `uncommitted` each such file once (a file edited after staging is one), and `untracked` files that are neither tracked nor ignored; ignored files are never read, and submodules are not entered. What "unpushed" means, by `unpushedBasis`: `upstream` is the branch's configured upstream as that tracking ref stands in this repository, however stale, and `unpushed` is the `+N` of `# branch.ab` (commits behind are not counted); `remotes` is a branch with no upstream, or whose upstream ref is gone, in a repository that has at least one remote, and `unpushed` is the commits of HEAD that no remote-tracking ref contains, so a branch cut from `origin/main` with nothing added is 0 and a remote that was added but never fetched makes every commit count; `local-only` is a branch with no upstream in a repository with no remote at all, reported as such with `unpushed` 0 instead of counting every commit; `detached` is a detached HEAD, where `unpushed` is the commits that no local branch and no remote-tracking ref contains (a commit a branch still points at is not at risk), whether or not there is a remote; `no-commits` is a repository before its first commit, which has nothing to push. Caps: each count stops at 1000 (`COUNT_CAP`), `rev-list` stops at the same number so a long history is never walked in full, the status listing is cut at 512 KiB (`SUMMARY_LIST_CAP`, killing the process rather than reading on), and `truncated` is true when any count reached the cap or the listing was cut, so every number is then a floor; the client prints `1000+`. The client (`src/lib/moshpit/close-check.ts`, `fetchChangesSummary` and `unsavedWork` in `changes.ts`, `confirm-close.tsx`, `agent-detail.tsx`) opens the Close dialog at once and starts the read as it appears; until the answer arrives the line says "Checking the checkout…" and Close pane is disabled, Cancel keeps focus and Escape works. A clean checkout, or a directory that is not a checkout, or a repository with no remote, leaves the dialog exactly as it was. Work found says what was found in plain words ("This checkout has 2 uncommitted files, 1 untracked file, 1 commit not pushed."), says Close ends the pane and does not delete or change any files, offers View changes, and keeps Close pane disabled until "close" is typed (ignoring case and surrounding spaces; Enter confirms only when it matches). A failed check says so, with the reason, and asks for the same word. The field has a visible label, is 16 px, and sits with the buttons in a footer that does not scroll, so with the keyboard up at 390 px the label, field and both buttons stay on screen while the text above them scrolls. The answer is never kept: each opening runs a fresh read, a read still running when the dialog closes is aborted, and a late answer is ignored. A shell's own Close dialog and demo mode (no bridge URL) make no check. Decisions the spec did not dictate, each reversible where it is made. (1) A repository with no remote at all is not a warning on its own: closing a pane cannot strand commits that only ever lived in a repository the user still has, and counting them would warn on every scratch directory. Treat `local-only` as work in `unsavedWork` to reverse it. (2) A detached HEAD is judged against branches as well as remotes, not remotes alone: a commit that no branch holds is the one `git gc` can drop. (3) A branch without an upstream is judged against every remote-tracking ref, so work pushed under another name counts as pushed; name one remote in the `rev-list` call to make that stricter. (4) The staged and unstaged counts are in the response and the tests but the dialog says only "uncommitted files", since staged and unstaged overlap. (5) Stashes, unpushed commits inside a submodule, and a worktree on another branch are not looked at. (6) View changes closes the Close dialog and opens the Changes sheet, because two modal layers would fight over focus; the user taps Close pane again afterwards, which runs a new check. (7) The client waits 20 s for the answer, then treats the check as failed; the bridge's own limit is 30 s. (8) The typed-consent field is not focused when the dialog opens, so Cancel stays the safe default and a phone's keyboard does not rise by itself. **C12. Send any file to an agent.** Accept any file from the picker or share sheet (with C7), not only images. The bridge writes it to a private per-upload directory on the host under S3 size bounds, never overwrites, and inserts the quoted path into the draft without sending. **C13. Alert timing that matches herdr.** Read herdr's own `[ui.sound]` and `[ui.toast]` config through the bridge, read-only, so C8 cues and push follow the TUI: per-agent on/off, a `delay_seconds` after which an attention alert fires only if the agent is still blocked, and no finished alert for the agent already on screen. **C14. Last-turn and session scopes in the Changes sheet.** C3 answers "what is uncommitted?". Add two more scopes to the same sheet: Last turn, the changes since the agent's current or latest turn began, and Session, everything since the session was first seen. Both need a baseline that git does not keep, so the bridge records one per canonical pane plus native session when herdr reports the agent going from idle to working, and once when the session first appears. The proposed baseline is a tree ID written through a private temporary index (`GIT_INDEX_FILE`, `add -A`, `write-tree`), leaving the real index, the worktree, HEAD and every ref untouched; the diff is then `git diff <tree>` against the working tree under C3's caps. Baselines are private bridge state, bounded per session, and a missing one shows "No baseline for this turn", never a guessed diff. Unreferenced tree objects can be pruned by `git gc`; treat a pruned baseline as missing. Changes by anything else in the same checkout during the turn are included, and the sheet says so. This is the first time the bridge would write into a project's object store, and it makes the bridge react to status transitions, so it needs an owner decision. Probe first: the cost of `add -A` on a large checkout, and whether herdr's working transition arrives before the agent's first edit.

**C15. Read-only file view and file search.** From a C3 file row, open the whole file; from the sheet's header, search file names in the checkout. Proposed `GET /api/files?target=<pane>&path=<relative>` and `GET /api/files/search?target=<pane>&q=`. The bridge resolves the root from the herdr snapshot as in C3, takes names from `git ls-files` plus untracked-not-ignored files, and refuses anything that leaves the root after resolving symbolic links. Ignored files are never listed or served, which keeps `.env` and build output out by default. Text only, capped at 1 MiB with a `truncated` flag, `no-store`, with syntax colouring on the client from a bundled highlighter. No writes, no directory tree beyond search results, no editor. **C16. Dev-server links for a pane.** Promoted from the smaller ideas. A loopback-only port is listed without a link, with one line saying it must be exposed by the operator, for example through the tailnet. **C17. Private notification text.** Web Push already encrypts the payload to the browser, so the push service cannot read it, but the notification itself can show the agent's name and prompt text on a lock screen (`public/sw.js` uses `data.name` and `data.prompt`). The bridge omits the withheld fields from the payload rather than leaving the worker to hide them, so nothing withheld leaves the host. Default stays full; the setting is offered when notifications are enabled.

Current: landed on 2026-10-10. Each saved subscription may carry a `privacy` of `full`, `name` or `generic`; a missing or unrecognised value reads as `full`, so existing `push.json` entries need no migration. `POST /api/push-subscription` accepts an optional `pushPrivacy` beside `pushSubscription`, or alone to change the level of the device's existing subscription; any other value is refused with 400 `push_privacy_invalid`, and a level sent when the device has no subscription with 409 `push_not_subscribed`. **C18. Non-exportable device key.** The device secret is a bearer value in `localStorage` (`access.ts`), so a copy of that storage is a working device. ### D1 plan gate for native iOS

This is a technical investigation sequence, not authorization to resume native delivery:

1. Correct Codemagic's project path to `ios/App/App.xcodeproj`, commit a shared App scheme, and configure team/profile/distribution signing through CI secrets. Prove a clean CI clone creates a signed installable IPA; local compilation alone cannot pass this gate.
2. Build/sync the existing `dist/spa` into the Capacitor shell and capture its actual HTTP/WebSocket Origin behavior on a device. Exercise identity, pairing, uploads, submissions, and tickets against an isolated bridge. Do not allow all opaque/custom origins to make the probe pass.
3. Decide whether the existing bridge can safely support the observed WebView boundary. Prefer the shared UI and narrowly scoped integration. If a native transport is required, specify ownership of credentials, session identity, receipts, and cancellation across the plugin boundary before adding it; there is no approved SSH/Mosh plugin design yet.
4. Measure suspension/resume on hardware and specify reconnect/draft recovery within supported iOS behavior. Do not add audio/VoIP background modes merely to keep a terminal alive. Native push and Live Activities need separate approval and entitlement design.

For the other deferred rows, the revisit condition is the plan gate. They have no implementation schedule or invented API design until demand or target-device evidence establishes a requirement.

## Decisions and completion rules

The ranking is a recommendation. Two gates are closed. S4 expiry timing keeps the existing poll, decided on 2026-09-21 and recorded in its section. `GET /api/vapid` stays readable without a device inside the existing origin/authority boundary, decided on 2026-09-24: the VAPID public key exposes no device data, grants no subscription or delivery authority, and doubles as the app's "is this a bridge" probe. Three more closed on 2026-09-24: the S3 proposed limits and log retention are approved as written in the S3 table, the S3 CSP restriction to `MOSHPIT_CONNECT_ORIGINS` is approved with its browser case driven through a bridge-served SPA, and S13 is adopted as a separate migration after S5-S6. S7 host storage stays plain private JSON and files, with no SQLite or application encryption, decided on 2026-09-26 and recorded in the S7 implementation plan. S7 release trust was decided on 2026-09-27, superseding the two signing decisions below: releases are not signed. An Ed25519 key held as an Actions secret added no trust beyond GitHub itself, because anyone who can change the workflows or the secret can publish a signed release, and it left a key to generate, rotate and revoke. `moshpit update` trusts HTTPS from GitHub and the release manifest: it checks the executable's SHA-256 and size against the manifest before anything runs. This catches a damaged download, not a compromised GitHub account or repository, and the documentation says so. A private repository's assets are read with `MOSHPIT_GITHUB_TOKEN` or `GH_TOKEN`, sent only to `api.github.com` and `github.com` over HTTPS. Superseded on 2026-09-27: S7 release signing was decided on 2026-09-26. Releases are signed with Ed25519 as raw signatures over the executable and over its manifest, checked by Node's `crypto.verify` and by `openssl pkeyutl -verify -rawin` (OpenSSL 3). The maintainer holds the private key as the `MOSHPIT_RELEASE_SIGNING_KEY` Actions secret. The public key is committed at `deploy/release-signing.pub.pem` and embedded in each executable, and the release page publishes its fingerprint (the SHA-256 of the DER public key). Releases are hosted on GitHub Releases and built on native x64 and arm64 runners (`ubuntu-24.04`, `ubuntu-24.04-arm`). The release serial is the commit count of the tagged commit. Generating and installing the real key is the maintainer's manual step with `scripts/release-key.mjs`, which never installs anything itself. Also superseded: S7 update trust was decided on 2026-09-27. `moshpit update` trusts only the key embedded in the running executable, and never a key served beside a release. A release may embed a new key; it is accepted only when the current key signed it, and every later update is verified against the new key. There is no revocation: whoever holds a leaked key can sign an update that installs, so recovering from a leak means a new key and a manual reinstall of a release that embeds it. No policy gate remains open.

Each implementation should update its status with the landed commit, actual checks, and remaining limitations. Keep implementation status separate from V1 evidence. A source-only review, an unrun test, a blocked helper, and a disabled feature are not passing release checks. Security and correctness changes need a runnable regression at the shared boundary they fix; documentation-only work does not require an unrelated full application test run.
